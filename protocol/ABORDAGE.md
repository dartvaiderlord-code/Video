# Абордаж / Abordage 1

Новый протокол доставки экрана и звука нативным клиентам. Видеотракт не использует PeerConnection, RTP, SDP, STUN/TURN или оценку пропускной способности WebRTC. Кодеки — стандартные H.264 и AAC внутри MPEG-TS; собственные кодеки и криптографические примитивы не изобретаются.

## Путь данных

Windows: DXGI через FFmpeg `ddagrab` → D3D11 масштабирование/конвертация NV12 → H.264 NVENC/AMF (либо QSV с копированием NV12, явно выбранный libx264 с программной конвертацией). WASAPI отдельно захватывает выбранное приложение с дочерними процессами либо системный звук с исключением процесса клиента. В режиме Абордажа это 48 кГц stereo и короткий буфер. FFmpeg кодирует AAC и мультиплексирует TS. Локальный UDP передаёт TS транспортному worker, работающему в отдельном Dart isolate.

Worker группирует до 48 TS-пакетов (9024 B), шифрует блок и фрагментирует. Один поток UDP идёт на сервер. Сервер проверяет подлинность и рассылает зашифрованный блок зарегистрированным зрителям. Worker зрителя собирает/FEC-восстанавливает/расшифровывает TS. При позднем подключении ждёт random-access PES видео PID 256 и сохраняет два блока PAT/PMT preroll, затем передаёт TS локальному плееру. Android использует MediaCodec через libmpv/media_kit, Windows — D3D11VA. В интерфейс Flutter не пересылаются сырые видеокадры через MethodChannel.

HTTPS/WSS остаётся для авторизации комнаты, приглашений, текста, ключей и запросов повторной передачи. Опциональный разговор через микрофоны пока использует отдельный существующий WebRTC audio-only mesh; он не управляет видеобитрейтом. Браузерные комнаты продолжают использовать прежний WebRTC. Браузер не может смотреть комнату Абордажа; сервер выдаёт понятную ошибку.

## Создание и подключение

`create` дополнительно содержит `media:{protocol:"abordage-1",width:1920,height:1080,fps:120,mbps:50}`. `join` содержит `supports:["abordage-1","webrtc"]`. Обычные проверки ссылки, кода и лимита зрителей остаются обязательными.

После успешной авторизации `created`/`joined` содержит `abordage`:

- `id`: случайный 8-байтный ID UDP-подключения, hex;
- `key`: случайный персональный 32-байтный ключ HMAC, hex;
- `cipherKey`: случайный ключ XChaCha20-Poly1305 комнаты, 32 байта, hex;
- `noncePrefix`: случайные 20 байт, hex;
- `port`: публичный UDP-порт; `host` — необязательный адрес, иначе HTTPS hostname;
- `profile`: согласованный запрос разрешения/FPS/битрейта.

Ключи выдаются только через уже подтверждённое TLS-соединение. Нативный клиент сначала посылает HELLO и ждёт проверенный ACK, затем начинает медиа. Без UDP-порта соединение завершается с ошибкой; скрытого перехода на TCP или снижения качества нет. IPv4 relay обеспечивает обычный исходящий NAT: пользователям не нужно пробрасывать порты домашних роутеров. Входящий UDP открывается только на сервере. IPv6-only сеть и заблокированный UDP в эту версию не входят.

## Датаграмма

Все целые unsigned, big-endian. Длина — от 48 до 1184 байт, включая MAC. Размер ниже обычного MTU IPv4/IPv6; path MTU меньшего размера отдельно не определяется.

| Смещение | Размер | Поле |
|---|---:|---|
| 0 | 4 | ASCII `ABR1` |
| 4 | 1 | Тип: HELLO=1, ACK=2, DATA=3, PING=4, PONG=5 |
| 5 | 1 | Flags=0 |
| 6 | 1 | Индекс shard; parity имеет индекс `count` |
| 7 | 1 | Число data shards, 1–8 |
| 8 | 8 | ID подключения |
| 16 | 4 | Номер датаграммы, без повторного использования |
| 20 | 4 | Номер шифрованного блока, начиная с 1 |
| 24 | 4 | Полная длина ciphertext + AEAD tag |
| 28 | 4 | Монотонная отметка времени отправителя, ms |
| 32 | 0–1136 | Payload |
| конец−16 | 16 | Первые 16 байт HMAC-SHA256(header + payload) |

HELLO/ACK/PING/PONG имеют пустой payload и нулевые shard/length поля. ACK/PONG возвращают номер соответствующего запроса. Клиент принимает только ожидаемый, ещё не использованный номер подтверждения. Сервер меняет NAT endpoint только после свежего HELLO/PING с правильным MAC. Повторные номера отвергаются окном 256 пакетов. DATA принимается только от капитана с зарегистрированного адреса. При рассылке ID/MAC заменяются персональными для зрителя. Прямого доступа между комнатами нет; после закрытия WSS регистрация удаляется.

## Шифрование и FEC

Реализация XChaCha20-Poly1305 — **Monocypher 4.0.2**, нативная FFI-библиотека Windows/Android. Независимая реализация Dart cryptography используется для сверки в тестах. Nonce: `noncePrefix[20] || block[4]`. AAD: `ABR1[4] || prefix[20] || block[4] || timestamp[4] || cipherLength[4]`, всего 36 B. Шифруется весь TS-блок; 16-байтный AEAD tag дописывается к ciphertext. Данные не передаются декодеру до успешной проверки AEAD.

Ключ/nonce не используются для разных plaintext. При исчерпании 32-битного номера нужна новая комната/ключ. Повторная отправка использует сохранённый ciphertext с новыми номерами датаграмм; повторного шифрования нет. Сервер знает ключ комнаты и является доверенной стороной; это не шифрование от владельца сервера.

Ciphertext разбивается на shards до 1136 B. Добавляется XOR parity длиной 1136 B, с нулевым дополнением короткого последнего shard. Один недостающий shard восстанавливается без запроса. FEC не исправляет произвольное число потерь и увеличивает трафик.

## Восстановление и задержка

Неполный блок после 8 ms может вызвать WSS `abordage-nack` с максимум четырьмя номерами. Не более 20 запросов/с от worker. Сервер передаёт запрос только капитану этой комнаты. Капитан хранит максимум 512 зашифрованных блоков до 250 ms и пересылает весь запрошенный блок. Серверная рассылка также доставит повтор другим зрителям; уже полученные блоки они проигнорируют.

Сборщик держит максимум 128 блоков и ждёт восстановления до 120 ms с момента первого shard/наблюдаемого пропуска. После срока пропускает повреждённый блок, продолжая живой поток. Это может вызвать артефакты до следующего IDR: GOP около 250 ms. В обычном случае полные/FEC-восстановленные блоки идут сразу. Локальный UDP output FFmpeg равномерно выдаёт TS с ограничением burst; таймер упаковки TS — 3 ms; входящая/исходящая очередь ограничена. Нельзя обещать нулевую задержку или отсутствие потерь на перегруженном канале.

## Качество и проверка

По умолчанию запрос 1920×1080, 120 FPS, 50 Мбит/с, GPU auto. B-кадры/lookahead отключаются, NVENC использует ultra-low-latency и delay=0. Внешнего фильтра увеличения FPS нет (`fps_mode=passthrough`). `ddagrab dup_frames=1` поддерживает постоянный кадровый ритм и периодические IDR даже на неподвижном экране, чтобы новые зрители могли подключаться. Повторы неподвижного/медленного источника входят в encoded FPS; они не создают новые фазы движения. SPS/PPS повторяются у keyframes через `dump_extra`. Для 120 разных кадров нужен соответствующий монитор, источник, GPU, декодер и частота экрана зрителя.

Одна отправка капитана экономит uplink; серверу требуется исходящий канал на всех зрителей плюс FEC/MAC/повторы. Автоматического уменьшения разрешения/FPS/битрейта из WebRTC нет. При нехватке ресурсов пропуски остаются возможны. GPU auto не подменяется программным кодированием молча; CPU выбирается явно.

`sh native/tool/test_abordage.sh` проверяет **320×180/480 FPS** и **640×360/240 FPS** с настоящими H.264 encode/decode и 25/50 Мбит/с. Зритель подключается после начала эфира. Между клиентом и настоящим Node UDP relay удаляются одиночные/двойные shards и вносится перестановка. Кадры содержат бинарную отметку wall-clock, которая читается из декодированных пикселей: latency включает кодирование, транспорт и декодирование, без синхронизации с дисплеем. Проверяются actual decoded FPS, принятый битрейт, восстановление и отсутствие decoder errors в измеряемом интервале. Это не измерение 1080p/120 на физических Windows/Android или через домашний интернет.
