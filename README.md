# Пиратский трактир

Трансляция экрана и доступного браузеру звука друзьям через WebRTC. Ведущий выбирает вкладку, окно или экран и отправляет ссылку. Зритель открывает её в браузере. Клиентская программа не нужна.

Видео и аудио идут напрямую каждому зрителю, при сложном NAT — через TURN. Сервер Node.js обслуживает интерфейс и WebSocket-сигнализацию, не записывает медиа. TURN пересылает зашифрованные WebRTC-пакеты. По умолчанию один ведущий и до 6 зрителей. Комнаты исчезают при отключении ведущего или перезапуске сервера. Переподключение ручное; новый эфир создаёт новую ссылку.

## Быстрый запуск на Ubuntu

Нужны Docker Engine с Compose plugin, Git и OpenSSL. HTTPS и TURN работают в отдельных контейнерах; настройки не зависят от домена, Snikket или сертификатов других приложений. По умолчанию используются отдельные порты: сайт 8443, локальный backend 3100, TURN 3479, UDP-реле 40000–40060.

```sh
git clone https://github.com/dartvaiderlord-code/Video.git
cd Video
# Замените пример публичным IPv4 своего сервера:
sh deploy/configure.sh 203.0.113.10
# Или используйте DNS-имя, A-запись которого указывает на сервер:
# sh deploy/configure.sh screen.example.com 203.0.113.10

docker compose -p screenroom -f compose.yaml -f compose.selfsigned.yaml -f compose.turn.yaml up -d --build
```

Скрипт создаёт `.env` с правами 600, генерирует случайный TURN_SECRET. Существующий `.env` не перезаписывается: при обновлении сохраните файл и редактируйте нужные параметры вручную. В DOMAIN указывайте DNS-имя или IPv4 без схемы/порта/пути. Генератор пока не поддерживает IPv6-адреса. PUBLIC_ORIGIN должен точно совпадать с адресом в браузере, без завершающего `/`.

Откройте **`https://ВАШ_АДРЕС:8443`**, придумайте код комнаты (4–64 символа), выберите экран/вкладку и отправьте друзьям ссылку и код. Зрители вводят этот код перед подключением; он не включается в ссылку. TURN_SECRET в интерфейс не вводится и друзьям не передаётся.

Перед запуском убедитесь, что выбранные порты и диапазон не используются другими приложениями. Не останавливайте действующие сервисы. В частности, 3000/3001 могут быть заняты, а существующий XMPP/TURN — занимать 3478/5349 и UDP 49152–65535. Наличие host network означает, что колонка PORTS в `docker ps` может быть пустой при занятых портах.

```sh
sudo ss -lntup '( sport = :8443 or sport = :3100 or sport = :3479 )'
sudo ss -lnup 'sport >= :40000 and sport <= :40060'
```

Диапазоны, зарезервированные другим приложением для будущих UDP-сессий, нужно проверять в его настройках. Если порты заняты, задайте другие до генерации конфигурации:

```sh
HTTPS_PORT=9443 APP_PORT=3200 TURN_PORT=3480 TURN_MIN_PORT=41000 TURN_MAX_PORT=41060 sh deploy/configure.sh 203.0.113.10
```

При ручном изменении `.env` одновременно обновляйте HTTPS_PORT и PUBLIC_ORIGIN; для TURN — TURN_PORT и TURN_URLS. Внутренние порты контейнеров приложения и Caddy остаются 3000 и 8443.

## Самоподписанный сертификат

Caddy автоматически создаёт локальный центр сертификации с самоподписанным корневым сертификатом и выпускает HTTPS-сертификат для вашего DOMAIN. Сертификаты и CA сохраняются в Docker volume `screenroom_caddy_data`; продление автоматическое. Не удаляйте этот volume при обновлениях. Новые устройства по умолчанию не доверяют такому CA и покажут предупреждение. Для IP-адреса публичный домен не требуется, обращаться нужно по адресу, указанному в DOMAIN.

В браузере можно попробовать вручную принять исключение **для этого сайта**, если браузер это позволяет. Для передачи экрана нужен защищённый контекст и доступный `getDisplayMedia`; одного обхода предупреждения не на каждом устройстве достаточно. Если захват экрана/WebSocket блокируется, добавьте корневой сертификат этого сервера в доверенные на устройстве/в браузере. Не отключайте проверки TLS глобально. Caddy не устанавливает свой CA в доверенные на хосте автоматически.

Экспорт **публичного** корневого сертификата после первого запуска:

```sh
docker compose -p screenroom -f compose.yaml -f compose.selfsigned.yaml -f compose.turn.yaml exec -T caddy cat /data/caddy/pki/authorities/local/root.crt > screenroom-root.crt
openssl x509 -in screenroom-root.crt -noout -sha256 -fingerprint
```

Передайте `screenroom-root.crt` друзьям по доверенному каналу и сверяйте SHA-256 fingerprint. Порядок установки зависит от ОС: хранилище доверенных корневых CA в Windows/macOS/Linux, а Firefox может использовать отдельное хранилище. На iOS после установки профиля потребуется явно включить полное доверие; поддержка захвата экрана с мобильного браузера всё равно ограничена. Передавайте только `root.crt`, **не ключи CA и не весь volume**. Доверяйте этому CA только если доверяете владельцу сервера: он способен выпускать сертификаты для других имён.

При смене DOMAIN обновите PUBLIC_ORIGIN и выполните исходную команду `up -d --build`. Caddy выпустит новый сертификат через тот же сохранённый CA. Потеря volume создаст новый CA: доверие на устройствах придётся настроить заново. Не запускайте одновременно разные HTTPS overrides: `compose.selfsigned.yaml`, `compose.https.yaml` и `compose.existing-cert.yaml` — альтернативы.

## Firewall и TURN

Для рекомендованной конфигурации разрешите входящие **TCP 8443, TCP/UDP 3479, UDP 40000–40060** в firewall сервера и провайдера. Если UFW уже активен:

```sh
sudo ufw allow 8443/tcp
sudo ufw allow 3479/tcp
sudo ufw allow 3479/udp
sudo ufw allow 40000:40060/udp
```

Не включайте и не сбрасывайте firewall целиком ради приложения. Backend публикуется только на 127.0.0.1 и не требует открытия порта наружу.

TURN использует Linux host network, public IPv4 непосредственно на сервере и временные пароли на 12 часов. Для более длинного эфира создайте новую комнату. При NAT перед сервером потребуется проброс TURN-порта и всего relay-диапазона и соответствующая настройка external/local IP coturn; этот вариант отдельно не проверен. Поставка включает TURN UDP и TCP, без TURN TLS. Для сетей, разрешающих только TLS/443, нужен отдельный TURNS endpoint с сертификатом и общим секретом (например `turns:turn.example.com:5349?transport=tcp`), который задаётся через TURN_URLS/TURN_SECRET.

В интерфейсе зрителя показано «Прямое соединение» или «Через TURN». Можно запустить без TURN: оставьте TURN_URLS пустым и не добавляйте `-f compose.turn.yaml`. За некоторыми домашними NAT соединение тогда не установится.

## Качество, задержка и звук

- WebRTC передаёт медиа без HLS-сегментов и серверного перекодирования. Фактическая задержка зависит от устройств, сети, кодирования и TURN. RTT в интерфейсе — сетевое время обмена, не полная задержка картинки.
- Доступны 720p, 1080p, 1440p и 4K; 30, 60, 120, 144, 165 и 240 FPS; 4, 8, 12, 20, 35, 50, 80, 100, 150 и 200 Мбит/с на зрителя. Для качества начните с одного зрителя, 1080p/120 и 35–50 Мбит/с; для надёжного высокого FPS используйте Windows-клиент с DXGI. Высокий FPS передаётся в ограничения захвата и настройки WebRTC-отправителя; браузер/ОС могут ограничить результат. Под видео показаны параметры захвата у ведущего и реально декодируемые кадры у зрителя. Разрешение/FPS — пожелания браузеру; битрейт — согласованный бюджет с повышенной стартовой/минимальной целью, а не требование тратить трафик на статичный кадр.
- Каждый зритель расходует исходящий канал ведущего: 3 × 8 Мбит/с ≈ 24 Мбит/с плюс аудио и служебный трафик. При нехватке снижайте качество или число зрителей; для большой аудитории нужна архитектура с SFU.
- Рекомендуются Chrome/Edge на компьютере. Надёжный способ передать звук — выбрать **вкладку** и включить передачу аудио. Захват системного звука игр/приложений зависит от ОС и браузера; на Linux/macOS может отсутствовать. Интерфейс сообщает, выбран ли звук.
- Мобильные браузеры обычно могут смотреть, но не передавать экран. При блокировке автозапуска нажмите «Включить видео и звук». DRM-видео может давать чёрный экран.
- Любой получивший ссылку и код комнаты может смотреть и переслать их. Ключ после `#` не попадает в HTTP access log, но передаётся серверу сигнализации по WSS. P2P раскрывает участникам сетевые адреса. Авторизация пользователей, запись, удалённое управление и защита от крупных DDoS в проект не входят.

## Проверка и обновление

```sh
docker compose -p screenroom -f compose.yaml -f compose.selfsigned.yaml -f compose.turn.yaml ps
curl --fail http://127.0.0.1:3100/healthz
# После экспорта root.crt; замените адрес своим, не используйте --insecure:
curl --cacert screenroom-root.crt --fail https://203.0.113.10:8443/healthz
```

Проверьте движущуюся картинку, звук и задержку с другом из другой сети; повторите для нужной ОС и источника звука. Для проверки NAT попробуйте зрителя через мобильный интернет. Автотесты с синтетическим медиа не заменяют такую проверку.

Обновление: `git pull --ff-only`, затем та же команда Compose `up -d --build`. Перезапуск сбрасывает комнаты. Сохраняйте `.env` и Docker volumes. Самоподписанный режим не зависит от чужих сертификатов и не меняет конфигурацию действующих сайтов. Публичный Docker-образ пока не публикуется: Compose собирает его из исходников.

Логи (не передавайте содержимое `.env`, ключи и полный `docker inspect`):

```sh
docker compose -p screenroom -f compose.yaml -f compose.selfsigned.yaml -f compose.turn.yaml logs --tail=80
```

## Другие варианты HTTPS

- Уже настроенный reverse proxy: запускайте `compose.yaml` и при необходимости `compose.turn.yaml`, добавьте отдельный виртуальный хост на upstream. Host-installed proxy использует `127.0.0.1:APP_PORT`; контейнерный прокси нужно подключить к общей Docker-сети и направить на `app:3000`. Пример Nginx — `deploy/nginx.conf.example`.
- Публичный сертификат ACME: `compose.https.yaml`, DNS-имя и свободные 80/443; PUBLIC_ORIGIN без `:8443`. Caddy получает и продлевает сертификат автоматически.
- Собственный готовый сертификат: `compose.existing-cert.yaml`, DOMAIN, PUBLIC_ORIGIN, HTTPS_PORT, TLS_CERT_DIR, TLS_CERT_FILE и TLS_KEY_FILE. Каталог монтируется только для чтения, имена файлов задаются относительно него. Монтируйте также цели символических ссылок. Caddy перечитывает сертификат каждый час; продление — задача владельца сертификата. Настроек конкретного сервера в этом варианте нет.

## Разработка и тесты

Node.js 24 LTS, npm; БД и сборщик фронтенда не нужны.

```sh
npm ci
npm test
npm start
# Chromium для теста WebRTC:
npx playwright install --with-deps chromium
npm run test:browser
# Или с уже установленным Chromium:
CHROMIUM_PATH=/usr/bin/chromium npm run test:browser
```

Локально используйте localhost:3000. Код комнаты задаётся ведущим в интерфейсе и проверяется перед выдачей зрителю настроек подключения. Он хранится в памяти как хеш с солью; неверные попытки ограничены на комнату. Создавать комнаты могут посетители сервера. За HTTPS-прокси нужен точный PUBLIC_ORIGIN. Браузерный тест проверяет синтетическое видео, ненулевую энергию полученного аудио, приглашения, статистику и завершение.

В управляемой облачной среде Chromium может запрещать прямой UDP политикой WebRtcIPHandling. Для локального TURN/TCP-стенда без изменения политики:

```sh
CHROMIUM_PATH=/usr/bin/chromium npm run test:cloud
```

Нужен локальный Docker daemon. Скрипт создаёт временный coturn на случайном TCP-порту loopback и удаляет его после теста. Loopback peers разрешены только в этом тесте, не в production Compose.

Для Docker-сборки за корпоративным TLS-прокси предусмотрен необязательный BuildKit secret: `docker build --secret id=proxy_ca,src=/path/to/ca.pem -t screenroom .`. Проверка TLS при установке зависимостей не отключается.

## Обновление с первой версии

После `git pull --ff-only` повторите исходную команду Compose `up -d --build`. Старый `.env` и volume сертификатов сохраняются. Прежний глобальный ACCESS_KEY больше не используется: удалять его из `.env` необязательно. Ведущий теперь сам придумывает код для каждой комнаты, например GOIDA; зрители вводят тот же код. Старые комнаты завершатся при перезапуске. Создание комнат больше не закрыто общим серверным кодом; разворачивайте приложение для доверенного круга пользователей или ограничивайте доступ средствами своего прокси, если это необходимо.

## Нативные клиенты Windows и Android

В каталоге [`native/`](native/README.md) — отдельные приложения на Flutter/libWebRTC. Windows передаёт экран и системный звук, Android принимает трансляцию; комнаты совместимы с браузером. Есть выбор кодека, приоритет чёткости или FPS, запрос до 240 FPS / 200 Мбит/с и статистика фактической передачи. Инструкции сборки, импорта сертификата и проверки аппаратного ускорения — в README клиента. Сборка для обеих платформ настроена в GitHub Actions; наличие кода/настроек не заменяет успешную сборку и тест на устройствах.

## Версия 1.2.1: качество видео, звук приложений и чат

Обновите **сервер и оба нативных клиента**. Новые клиенты сохраняют совместимость видеокомнат со старым сервером, но чат требует обновлённой сигнализации. В каталоге сервера:

```sh
git pull --ff-only
docker compose -p screenroom -f compose.yaml -f compose.selfsigned.yaml -f compose.turn.yaml up -d --build
```

Используйте те же Compose-файлы и имя проекта, с которыми запущен ваш сервер; приведена стандартная self-signed/TURN конфигурация. `.env` и volume Caddy сохраняются. Текущий эфир завершится. Сертификат можно по-прежнему подтвердить в приложении без импорта root.crt.

В Windows выберите **экран DXGI**, 1080p, 120 FPS, 35–50 Мбит/с, VP8, включённое сохранение разрешения и FPS. Для 1440p/120 начните с 50–80 Мбит/с. Отдельный выбор звука: весь системный звук / без звука / одно приложение. Предпросмотр выключен по умолчанию. Выбирайте звук приложения, чтобы исключить уведомления других программ.

Текстовый чат и голосовой чат доступны в браузере, Windows и Android. Микрофон включается только после «Войти в голосовой чат»; его можно выключить, продолжая слушать. История чата на сервере не хранится. Для голосового чата рекомендуются наушники; браузерный захват системного звука может повторно захватывать голоса.

## Обновление контейнера для чата и пиратских имён (1.3.0)

В каталоге существующего проекта на Ubuntu, где находятся `.env` и `compose.yaml`:

```sh
git pull --ff-only
sh deploy/update.sh screenroom
```

Если использовалось другое имя Compose-проекта, подставьте его вместо `screenroom` (`docker compose ls` показывает имена). Скрипт находит существующий `app`, сначала собирает образ, затем пересоздаёт **только app** с `--no-deps`. `.env`, Caddy, TURN и volume сертификатов сохраняются. Действующая комната завершится: после обновления создайте новую.

Скрипт в конце проверяет `/api/version` внутри контейнера и должен вывести `Server 1.3.0: text and voice chat available`. Внешняя проверка версии: `https://ваш-адрес:порт/api/version`. Старый контейнер отвечает 404. Endpoint возвращает номер версии и поддержку `chat` / `voice`, без конфигурации и секретов. Перезапуск старого контейнера без сборки образа код сервера не обновляет.

В версии 1.3.0 зрители получают уникальные пиратские прозвища вместо кодов: например, Билли «Кривой Компас». Они одинаковы в переписке и голосовом чате. В Windows и Android добавлены флаг, ром и компас; постоянные подсказки убраны, настройки сертификата и дополнительные параметры свёрнуты. Кнопка капитана называется «Поднять флаг и отчалить». Алгоритм передачи видео и настройки качества в этом обновлении не меняются.
