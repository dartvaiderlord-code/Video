# Пиратский трактир — Windows и Android

Нативные Flutter-приложения с libWebRTC, без WebView. **Windows передаёт экран/окно и системный звук; Android смотрит.** Windows также умеет смотреть комнаты. Сервер и формат приглашений общие с браузером, переделывать существующий Docker-сервер не требуется.

## Что меняется в качестве

- Системный захват Windows и WASAPI loopback вместо браузерного диалога.
- H.264 как предпочтительный кодек для аппаратных реализаций; VP9/VP8 доступны на выбор и как совместимые резервные варианты. Аппаратное ускорение зависит от сборки WebRTC, драйвера и устройства — оно не гарантируется одним переключателем.
- 720p–4K, запрос 30–240 FPS, до 100 Мбит/с **на зрителя**. По умолчанию 1080p/60, 20 Мбит/с, приоритет чёткости.
- В режиме чёткости разрешение при перегрузке приоритетнее FPS; в режиме движения — наоборот.
- Нативная видеотекстура и декодер Android. Включён минимальный playout delay; на нестабильной сети это может увеличивать рывки.
- Видны фактические размеры, FPS, битрейт, кодек, доступные данные реализации кодера/декодера, причина ограничения качества и RTT/тип соединения.

Это не обещание 120/240 FPS: экран, игра, захват, кодировщик, исходящий канал, Wi-Fi и декодер телефона должны успевать. Например, три зрителя по 35 Мбит/с требуют около 105 Мбит/с исходящего канала ведущего. Нативный клиент не увеличивает скорость интернета. Начните с одного зрителя, 1080p/60, 20–35 Мбит/с, H.264 и проводного подключения Windows; сравните фактический FPS и ограничение bandwidth/cpu в статистике. Для 120 FPS нужен и экран/источник с соответствующей частотой.

## Использование

1. Windows: укажите точный HTTPS-адрес существующего сервера (например `https://ваш-сервер:8443`).
2. Если сервер использует собственный CA, импортируйте **публичный root.crt** и сверьте SHA-256 с владельцем. Обычному публичному сертификату импорт не нужен.
3. Выберите «Найти экраны и окна», источник, качество и код комнаты. Нажмите «Поднять флаг и передавать».
4. Передайте ссылку и код другу.
5. Android: вставьте полную ссылку, импортируйте тот же root.crt при необходимости, введите код и подключитесь. Доступны звук и полноэкранный просмотр; экран не гаснет, пока приложение на переднем плане.

Адрес сервера и доверенный публичный CA сохраняются локально. Код комнаты и приглашение автоматически не сохраняются. Дополнительное доверие привязано к выбранному HTTPS origin; глобального обхода TLS нет. Никогда не передавайте приватный ключ или весь volume Caddy. Доверяйте импортируемому CA только если доверяете его владельцу.

Windows-предпросмотр показывает только видео: локальная аудиодорожка не глушится, иначе пропал бы звук у зрителей. Системный звук не подменяется микрофоном. При отсутствии loopback приложение явно сообщает, что передаётся только изображение. Рекомендуются Windows 11, актуальный GPU-драйвер и Android с аппаратным H.264-декодером. Поддержка аудио отдельного окна зависит от версии Windows; сначала проверяйте весь экран. DRM и защищённые окна могут не захватываться.

При разрыве связи с сервером приложение освобождает захват; подключение нужно повторить. Выход ведущего завершает комнату, как в браузерной версии. Закрытие или перезапуск сервера также завершает комнату. Автоматическое переподключение и захват экрана Android не входят в эту версию.

## Сборка

Зафиксированы Flutter **3.38.5 / Dart 3.10.4** и flutter_webrtc **1.6.3**. Платформенные runners создаются стандартным `flutter create` из этой версии; bootstrap не перезаписывает Dart-код. Для обновления SDK/плагина отдельно повторяйте проверку совместимости.

```sh
cd native
python tool/bootstrap.py
flutter pub get
flutter analyze
flutter test
```

Windows: Visual Studio 2022 с Desktop development with C++ и Windows SDK, затем:

```powershell
flutter build windows --release
```

Распространяйте **всю** папку `build/windows/x64/runner/Release`, не только EXE: рядом нужны Flutter/libWebRTC DLL и assets. Приложение не подписано коммерческим сертификатом. На чистом Windows может потребоваться актуальный Microsoft Visual C++ Redistributable x64.

Android: JDK 17, Android SDK 36 и инструменты Flutter, затем:

```sh
flutter build apk --release --target-platform android-arm64,android-arm
```

APK: `build/app/outputs/flutter-apk/app-release.apk`. По умолчанию стандартный Flutter runner подписывает release APK локальным **тестовым debug-ключом**. Это сборка для личного тестирования, не публикация в Play Store. На разных машинах/CI ключ может различаться: для обновления такого APK может потребоваться удалить прежнюю установку с потерей локальных настроек. Для стабильных обновлений настройте собственный постоянный Android signing key в локальном защищённом хранилище/секретах CI, не в Git.

## GitHub Actions

Workflow `.github/workflows/native.yml` собирает Windows x64 и Android APK на соответствующих ОС, запускает анализатор и тесты и загружает артефакты `Pirate-Tavern-Windows-x64` и `Pirate-Tavern-Android-APK`. Его можно запустить вручную или изменением `native/**` в main. **Наличие workflow само по себе не означает успешную сборку**: скачивайте артефакты только из завершившегося зелёного запуска. Артефакты Actions не являются релизом в GitHub Releases.

## Проверки и пределы

Unit-тесты проверяют URL/приглашения, ограничения кода, параметры нативного захвата, отказ принимать ключи вместо CA, порядок сигнализации и Origin WebSocket. Интеграционный тест использует настоящий Node-сервер; отдельный TLS-тест создаёт временный сертификат через OpenSSL, подтверждает отказ без доверия и успешный WSS после импорта CA, сверяет SHA-256 с OpenSSL. Для этих тестов нужны Node.js и OpenSSL (они установлены на GitHub runners). Widget-тест проверяет экран Android-зрителя без запроса камеры/микрофона.

Отдельно необходимы на целевых устройствах: реальный захват Windows, WASAPI, выбор аппаратного кодека/декодера, H.264/VP8 совместимость с браузером, приём Android, TURN из разных домашних сетей, качество/задержка и длительная работа. Linux-тесты не подтверждают эти возможности. До такой проверки не считайте качество и FPS гарантированными.
